# 整理技术文档

在用户要求整理、重组或规范化技术文档时使用本技能。目标是提升结构清晰度、可读性和一致性。

## 使用时机

- 用户说「整理技术文档」「重组文档」「统一文档格式」
- 处理 README、API 说明、架构文档、项目描述文档
- 文档散乱、缺少目录、层级不清或风格不统一

## 整理流程

按以下顺序执行（可只做其中几步）：

1. **分析现状**：识别文档类型、现有标题层级、重复/缺失章节、术语是否统一。
2. **确定目标结构**：根据文档类型选用下方模板，或与用户确认期望结构。
3. **统一格式**：标题层级（如一级标题仅一个、二级为章节）、列表与代码块风格、中英文与空格。
4. **生成或更新目录**：若文档较长，在开头添加 TOC（Markdown 用 `## 目录` + 标题链接）。
5. **收尾检查**：用下方检查清单过一遍。

## 常用文档结构模板

### README / 项目说明

```markdown
# 项目名称
简短一句话说明。

## 目录
（可选，长文档时保留）

## 快速开始
安装、运行、最小示例。

## 功能 / 特性
（或「主要功能」）

## 配置
环境变量、配置文件说明。

## API / 使用说明
（按需）

## 开发 / 贡献
（按需）

## 许可证
```

### API 文档

```markdown
# API 名称 / 模块名
概述与约定（如 base URL、认证方式）。

## 目录

## 通用说明
错误码、分页、通用请求头等。

## 接口列表
### 模块 A
#### GET /xxx
- 说明
- 请求参数
- 响应示例
#### POST /yyy
...
### 模块 B
...
```

### 架构 / 技术方案

```markdown
# 文档标题
背景与目标（1–2 段）。

## 目录

## 架构概览
图示 + 简要说明。

## 模块 / 组件
每个模块职责、边界、依赖。

## 数据流 / 关键流程
（按需）

## 技术选型与约束
（按需）

## 扩展与演进
（按需）
```

## 格式与风格约定

- **标题**：一级标题仅一个（文档标题），章节用二级，小节用三级；标题前后空一行。
- **列表**：同一层级统一用 `-` 或 `*`；列表项若为句子，结尾可统一加或不加句号，但全文一致。
- **代码/配置**：用 fenced code block 并标注语言；行内代码用反引号。
- **术语**：全文统一（如「接口」与「API」二选一并固定；同一概念不用多个译名）。
- **中英文**：中文与英文/数字之间酌情加空格（视项目既有风格而定，保持一致）。

## 检查清单

整理完成后自检：

- [ ] 一级标题只有一个，层级递进合理（无跳级）
- [ ] 长文档有目录，且目录链接正确
- [ ] 同类内容归在同一章节，无重复段落
- [ ] 术语、缩写、专有名词全文一致
- [ ] 代码块与列表格式统一，无破损的 Markdown 语法
- [ ] 必要处有简短说明，避免「裸」列表或「裸」接口名

## 输出方式

- 若为单文件：直接输出整理后的完整文档（或明确标注「仅展示改动部分」）。
- 若为多文件：先列出整理方案与目录结构，再按文件逐段给出修改建议或改写内容。
- 若用户仅要「方案」：给出结构建议 + 检查清单结论，不直接改全文。

## 补充说明

- 若项目已有文档规范（如 `.cursor/rules`、`docs/README` 中的约定），优先遵循既有规范。
